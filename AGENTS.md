# Agents Guide

This repository implements a cloud-backed execution layer for Django’s Task framework, with the explicit goal of delegating asynchronous and long-running work to managed services on AWS and Azure. Any agent interacting with this codebase should treat it as infrastructure glue rather than a task execution engine. The project is responsible for enqueueing, scheduling, and invoking tasks via cloud-native primitives, not for running or persisting task results locally.

Agents should assume that the public API surface is primarily Django settings driven. Configuration is expressed through the `TASKS` setting, where each backend defines how tasks are serialized and handed off to the cloud provider. The correctness of the system depends heavily on matching these settings to externally provisioned resources such as SNS topics, SQS queues, EventBridge schedulers, Azure Service Bus entities, or Azure Storage queues. Agents must not attempt to auto-create or mutate cloud resources unless explicitly implemented in the backend code.

The payload contract is stable and intentionally minimal. Tasks are serialized as JSON containing the task name, positional arguments, and keyword arguments. Agents must preserve this contract when extending or consuming backends, as remote workers are expected to deserialize this payload and invoke application logic independently of Django’s request lifecycle. The decorated task functions in Django serve as signatures and enqueue points, not as guaranteed execution locations.

Task results are intentionally out of scope for this repository at its current stage. Although a `TaskResult` object is returned immediately upon enqueue, agents should treat it as a tracking handle rather than a promise of execution or persistence. Any worker or consumer implementation must explicitly call back into the Django application to update task state. Database-backed result storage is acknowledged as incomplete and should not be relied upon for production guarantees yet.

When working on AWS backends, agents must be aware of the semantic differences between SNS, SQS, EventBridge Scheduler, and Lambda asynchronous invocation. SNS and SQS provide fan-out and queue semantics respectively, while EventBridge Scheduler exists solely to compensate for the lack of native delayed delivery in SNS and SQS. Lambda asynchronous invocation bypasses queue semantics entirely and should be treated as fire-and-forget. Extensions or fixes must respect these behavioral boundaries rather than attempting to unify them artificially.

For Azure backends, agents should treat authentication as a first-class concern. The codebase supports both connection-string based authentication and credential-loader based authentication using Azure Identity. Any new backend or modification must continue to allow credential indirection via a callable loader to avoid hardcoding secrets or coupling the system to a single authentication strategy.

This project is explicitly marked as early-stage. Agents should prioritize clarity, explicit configuration, and defensive error handling over aggressive abstraction. Backward compatibility is important, but correctness and alignment with cloud provider semantics take precedence. Documentation and examples should be updated alongside code changes, especially when modifying configuration keys or backend behavior.

Contributions should align with the philosophy that engineering is a responsibility. Agents are expected to write changes that are understandable, auditable, and respectful of users who are integrating this library into production Django systems that rely on external cloud infrastructure.
